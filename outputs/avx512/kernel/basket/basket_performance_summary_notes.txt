Advisor caveats
---------------
1. Advisor labels the fp16 dominant loop "Scalar". This is wrong - it is
   __m256h intrinsics throughout, and perf shows 134M packed-half retired,
   zero scalar-half. Advisor's classifier does not recognise AVX-512 FP16.
   Cite perf counters, not Advisor, for vectorisation claims.
   (fp32's main loop IS correctly tagged Vectorized AVX512, so the two runs'
   Type columns are not comparable.)

2. No fp16 roofline roof exists - all compute roofs are SP/DP (+ BF16 AMX
   this kernel never touches). Headroom quoted is against a SINGLE-precision
   ceiling. A true fp16 roof would sit ~2x higher, so 14.1x / ~7% of peak
   overstates it; against an implied fp16 peak it is ~3.5%. Either way the
   kernel is nowhere near compute-limited.

Overall interpretation
----------------------
Main performance evidence:
- 2.2x lower runtime.
- 2.4x fewer retired instructions.
- 5.2x fewer L1 loads.
- 2.5x less memory traffic on the dominant loop.
- Similar operating frequency.
- Similar L1 miss rates.
- Very small L2 miss counts.
- LOWER IPC than fp32.

fp16 wins by doing less work per path, not by running the pipeline harder.
Do not "optimise" this kernel for higher IPC.

Advisor complements the perf results:
- fp32 execution split between the main kernel and Intel's SVML inverse-CDF.
- fp16 collapses into one dominant kernel.
- Arithmetic intensity increases (0.486 vs 0.016/0.092 FLOP/Byte).
- Memory traffic decreases substantially (5.117 GB vs 12.833 GB).

Caveat on the SVML difference: fp16 uses Giles' norminv_fp16 superdyadic
spline instead of SVML. That is an ALGORITHMIC difference in the Normal
transform, not a precision one - so part of the 2.2x is the RNG path, not
the Milstein arithmetic.


OpenMP scaling reproducibility
------------------------------
The saved basket_l0_scaling_sweep.txt is one execution of the sweep (itself a
median of 5 interleaved trials per row). The whole sweep was then repeated 5
times to check the ratio32 column is not a single-run artifact:

    eps      ratio32 across 5 runs        spread
  0.200    1.79 1.83 1.73 1.73 1.81       +/-0.05
  0.100    1.75 2.04 2.13 2.07 2.06       +/-0.19
  0.050    2.14 2.14 2.14 2.21 2.24       +/-0.05
  0.020    2.31 2.30 2.24 2.31 2.31       +/-0.04
  0.010    2.70 2.69 2.66 2.71 2.67       +/-0.03

The saved table's values (1.77, 2.16, 2.24, 2.32, 2.79) sit inside the spread
at every row. Absolute times are stable too -- fp32 at eps=0.01 read 134.6 ms
in all five runs -- unlike the scalar Lookback kernel, whose 1-thread column
shifted between runs on the same shared machine.

ratio32 climbs from ~1.78 at small N_0 to ~2.69 at eps=0.01, against a serial
ratio of 2.35x: threading amplifies the fp16 advantage rather than eroding it,
the same behaviour the scalar Lookback kernel shows.
